## 結論

**L4 での生成時間は測れなかった。** gcsfuse 経由の重み読み込みが遅すぎて、
生成処理に到達する前に 30分のタイムアウトで打ち切られた。

`TASK.md` が最重要としていた「重みの読み込み時間」については、

| 重みの読み込み | 60〜180秒 | **約27分（1629秒）** |

月額見積もり $36 のうち $33 がこの推定に乗っているため、
**現在の構成のままでは見積もりが成立しない。**

## 遅さの内訳

テクスチャモデルのロードは6コンポーネントから成るが、時間配分が極端だった。

```
Loading pipeline components: 3/6  [00:01]   ← 最初の3つは1秒
Loading pipeline components: 4/6  [25:41]   ← 4つ目だけで25分40秒
Loading pipeline components: 6/6  [25:42]   ← 残りは1秒
```

単一の大きなファイル（UNet と思われる）の読み出しだけが極端に遅い。
形状モデルは 7.2GB の単一 safetensors を67秒で読めているので、
ファイルサイズだけでは説明がつかない。

現在の `job.tf` は GCS ボリュームのキャッシュを設定していないため、
大きなファイルへのランダムリードが素通しになっているとみている。

## 失敗の中で確定したこと

- **L4 で動くこと自体は確認できた**（`nvidia-smi: 22.49 GB`）
- **GPU クォータは問題なし**。`gpu_zonal_redundancy_disabled = true` が効いている
- **イメージ取得は38秒**。9.47GB に削った効果が出ている
- **重みはキャッシュから正しく読まれた**。HuggingFace からの再ダウンロードは発生せず、
  20GB への絞り込みとディレクトリ構造は正しかった
- **形状のみなら67秒でロードできる**。`--disable_tex` 構成の現実味が上がった

読み取り専用マウントのため `refs/main` への書き込みが失敗するが、
`Ignored error` として処理され実害はない。

## 費用

L4 $1.16/時 × 約32分 = **約$0.62**。

## 手順から変更した点

**重みのアップロード対象を絞った。** `TASK.md` の手順5は
`~/.cache/huggingface/hub` を丸ごと上げるが、これは 91GB あり、
Hunyuan3D が実際に使うのは約20GB だけ。他プロジェクトの重みと
古いスナップショットを含んでいた。

`refs/main` が指すスナップショットのみを対象とし、
HuggingFace キャッシュの `snapshots/` は `blobs/` へのシンボリックリンク構造で
gcsfuse がリンクを解決できないため `cp -rL` で実体を展開した。

結果は 21.1GB（形状 7.2GB + テクスチャ 13GB）。

## Terraform の修正（3件）

1. provider に `billing_project` / `user_project_override` が無く、

   2回目の apply では通るため、新規プロジェクトでしか踏まない

# 第2回 — 完走

gcsfuse のファイルキャッシュを有効にして測り直した。**生成まで完走した。**

## 結論

| | 推定 | 実測 |
|---|---|---|
| コールドスタート込み1回 | — | **533秒** |
| 2回目（温まった状態） | — | **519秒** |
| L4 での生成時間（正味） | 75〜95秒 | **146秒** |
| 重みの読み込み | 60〜180秒 | **263秒** |

**1回目と2回目にほとんど差がない。** Cloud Run Jobs は実行ごとに新しい
コンテナを立てるため、モデルのロードが毎回発生する。gcsfuse のファイル
キャッシュもメモリ上にあるので実行をまたいで残らない。

「温まっていれば速い」という前提は、**ジョブ方式では成立しない。**

|---|---|---|---|
| コンテナ起動 | 約40秒 | — | |
| テクスチャモデルのロード | 185秒 | 約30秒 | |
| 形状モデルのロード | 78秒 | （上に含む） | |
| 形状生成 | 24.7秒 | 14.6秒 | 1.7x |
| 面数削減 | 12.7秒 | 7.0秒 | 1.8x |

生成処理が約2.2倍なのは、L4 のメモリ帯域が 4070 の約6割であることと整合する。

## 何が効いたか

gcsfuse のファイルキャッシュ有効化。

| | キャッシュ無効 | キャッシュ有効 |
|---|---|---|
| paint パイプラインのロード | **25分42秒** | **1分19秒** |

約20倍。同じ症状が gcsfuse#2828 と diffusers#10280 に報告されている。
safetensors の mmap によるページフォルトが1回ずつ GCS へのレンジリクエストに
なるためで、キャッシュを有効にすると初回にファイル全体を並列ダウンロードする。

## 到達までに踏んだ失敗（4回）

| 症状 | 原因 |
|---|---|
| 30分でタイムアウト | ファイルキャッシュ未設定 |
| 14秒で起動失敗 | `file-cache-max-size-mb` だけではキャッシュは有効にならない。`cache-dir` が要る |
| 16秒で起動失敗・ログ皆無 | in-memory ボリュームは `cr-volume:` で参照するだけでなく、コンテナにマウントも必要 |
| OOM (signal 9) | キャッシュ6GiB + アプリが 16GiB を超えた。4GiB に縮小して解決 |

さらに、キャッシュが効いた後に別の問題が表面化した。

`trust_remote_code` でカスタムパイプラインを読むとき diffusers は
`HF_HOME/modules` にコードを書き出すが、`HF_HOME=/models` は読み取り専用
マウントなので `[Errno 30] Read-only file system` で失敗する。
`HF_MODULES_CACHE=/tmp/hf_modules` で解決した。

このとき PR #2 で入れたガードが機能し、テクスチャ生成が動いていないのに
「成功」と報告する事態を防いでいる。

## 見積もりへの影響

月額 $36 の前提が崩れる。GPU 部分が $33 → $86 になり、**合計は約$88**。

打ち手は3つ考えられる。

1. **テクスチャをやめる** — テクスチャ生成108秒とテクスチャモデルのロード185秒が

3. **モデルのロード自体を速くする** — 263秒のうちテクスチャ側が185秒。
   `.bin` を除いて safetensors に寄せる案は未検証

## 積み残し

# 第3回 — 高速化の検証（打ち手3・4）

第2回で確定した「モデルロード263秒が毎回発生する」ことに対し、
2つの打ち手を検証した。

## 打ち手3: gcsfuse のチューニング → 効果なし

`file-cache-cache-file-for-range-read` の既定は false で、`.bin` は zip 形式の
ため範囲読みされる。キャッシュを素通りして低速パスに落ちている可能性を疑った。

| 区間 | 基準 | 範囲読みキャッシュ有効 |
|---|---|---|
| テクスチャモデルのロード | 185秒 | 185秒 |
| 形状モデルのロード | 78秒 | 76秒 |
| 全体 | 533秒 | 531秒 |

**差は測定誤差の範囲。** 同条件の実行4回が 516〜533秒（ばらつき3%）に
収まっているので、この結論は安全に出せる。

### 副産物: バッファはキャッシュ上限とは別枠でメモリを食う

`file-cache-download-chunk-size-mb=512` と
`file-cache-parallel-downloads-per-file=32` を同時に上げたところ OOM で落ちた。
これらのバッファは `file-cache-max-size-mb` に含まれず、
512MB × 32並列 = 最大16GB になる。既定のままにしておくこと。

## 打ち手4: safetensors 化 → 仮説は裏付けたが未実測

### 仮説は正しい

`is_safetensors_compatible` が **False** を返す。

```
text_encoder/pytorch_model.bin          ← .bin のみ
unet/diffusion_pytorch_model.bin
unet/diffusion_pytorch_model.safetensors
vae/diffusion_pytorch_model.bin
vae/diffusion_pytorch_model.safetensors
```

diffusers は「全コンポーネントに safetensors が揃っているか」で形式を決めるため、
text_encoder に .bin しか無いことが原因で **3.41GB の unet も pickle 版が
使われている。**

### 検証の実装は2回とも失敗した

| 方法 | 結果 |
|---|---|
| バケットから .bin を削除 | HF が Hub と照合して欠けたファイルを再DLしようとし、読み取り専用の blobs/ に書けず失敗 |
| ＋ HF_HUB_OFFLINE=1 | 展開済みコピーは blobs/ を持たないため、オフラインではリビジョンを解決できず失敗 |

**HF のキャッシュはファイルを間引ける構造ではない。**
`cp -rL` で展開したコピーはオンラインなら動くが、オフライン解決には使えない。

### 正しい検証方法

`.bin` を消すのではなく、コード側で `use_safetensors=True` を渡す。

```python
# hy3dgen/texgen/utils/multiview_utils.py
pipeline = DiffusionPipeline.from_pretrained(
    multiview_ckpt_path,
    custom_pipeline=custom_pipeline_path, torch_dtype=torch.float16,
    trust_remote_code=True,
    use_safetensors=True)
```

バケットに手を入れず HF の照合とも衝突しないが、イメージの再ビルドが要る。

### 見込まれる効果

| 経路 | スループット |
|---|---|
| 形状モデル（safetensors、hy3dgen が直接読む） | 約95MB/s |
| テクスチャ（.bin、diffusers 経由） | 約48MB/s |

safetensors 経路が同等の速度になるなら、テクスチャのロードは 185秒 → 約95秒。
1回あたり 533秒 → 約440秒（$0.142）、月500生成で $86 → $71。

**約17%の改善**にとどまり、打ち手1（サービス化）や打ち手2（テクスチャ廃止）に
比べると小さい。
