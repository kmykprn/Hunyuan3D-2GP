## 結論

**L4 での生成時間は測れなかった。** gcsfuse 経由の重み読み込みが遅すぎて、
生成処理に到達する前に 30分のタイムアウトで打ち切られた。

`TASK.md` が最重要としていた「重みの読み込み時間」については、
推定を大きく外しているという形で答えが出ている。

|---|---|---|
| 重みの読み込み | 60〜180秒 | **約27分（1629秒）** |

月額見積もり $36 のうち $33 がこの推定に乗っているため、
**現在の構成のままでは見積もりが成立しない。**

## 遅さの内訳

テクスチャモデルのロードは6コンポーネントから成るが、時間配分が極端だった。

```
Loading pipeline components: 3/6  [00:01]   ← 最初の3つは1秒
Loading pipeline components: 4/6  [25:41]   ← 4つ目だけで25分40秒
Loading pipeline components: 6/6  [25:42]   ← 残りは1秒
```

単一の大きなファイル（UNet と思われる）の読み出しだけが極端に遅い。
形状モデルは 7.2GB の単一 safetensors を67秒で読めているので、
ファイルサイズだけでは説明がつかない。

現在の `job.tf` は GCS ボリュームのキャッシュを設定していないため、
大きなファイルへのランダムリードが素通しになっているとみている。

## 失敗の中で確定したこと

- **L4 で動くこと自体は確認できた**（`nvidia-smi: 22.49 GB`）
- **GPU クォータは問題なし**。`gpu_zonal_redundancy_disabled = true` が効いている
- **イメージ取得は38秒**。9.47GB に削った効果が出ている
- **重みはキャッシュから正しく読まれた**。HuggingFace からの再ダウンロードは発生せず、
  20GB への絞り込みとディレクトリ構造は正しかった
- **形状のみなら67秒でロードできる**。`--disable_tex` 構成の現実味が上がった

読み取り専用マウントのため `refs/main` への書き込みが失敗するが、
`Ignored error` として処理され実害はない。

## 費用

L4 $1.16/時 × 約32分 = **約$0.62**。

## 手順から変更した点

**重みのアップロード対象を絞った。** `TASK.md` の手順5は
`~/.cache/huggingface/hub` を丸ごと上げるが、これは 91GB あり、
Hunyuan3D が実際に使うのは約20GB だけ。他プロジェクトの重みと
古いスナップショットを含んでいた。

`refs/main` が指すスナップショットのみを対象とし、
HuggingFace キャッシュの `snapshots/` は `blobs/` へのシンボリックリンク構造で
gcsfuse がリンクを解決できないため `cp -rL` で実体を展開した。

結果は 21.1GB（形状 7.2GB + テクスチャ 13GB）。

## Terraform の修正（3件）

実機で apply して判明したもの。詳細は各コミットを参照。

1. provider に `billing_project` / `user_project_override` が無く、
   予算APIの呼び出しが gcloud の既定プロジェクトに紐づいて `SERVICE_DISABLED`
2. 請求先アカウントが JPY 建てなのに `currency_code = "USD"` 固定で
   `400 INVALID_ARGUMENT`。`currency_code` の指定をやめて解決
3. `iam.googleapis.com` の有効化漏れと、サービスアカウントの `depends_on` 欠落。
   2回目の apply では通るため、新規プロジェクトでしか踏まない

前提そのものを再検討することになる。
